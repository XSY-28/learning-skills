# 软件项目：从历史变化解释当前系统

只在学习对象是软件项目，且需要实际代码或版本历史时使用。目标是找到能解释当前行为的关键变化，不是穷举提交或做代码审查。

## 从当前任务限定检索范围

先按仓库说明检查环境和变化文件。Git 操作前检查 `git status --short`，保留现有未提交内容；说明当前读取的是哪个版本或工作区。默认只读，不为阅读历史切分支、回退、安装依赖或运行未知历史代码。

以一个用户可见任务定位入口、状态变化、关键模块和外部边界。读当前实现与相关文档，先提出待核实的问题，例如“任务状态为什么从内存移到数据库”。不要从目录名字推断已实现的保证。

## 从概览逐步缩小到证据

- 先看与目标有关的版本/发布节点和有限的提交概览，再按路径、关键词或时间区间缩小。按材料密度控制检索量，不默认全量读取 Git 历史。
- `git log --oneline -- <path>` 帮助找候选；需要跟踪单文件改名时可用 `git log --follow -- <file>`。这些只是检索工具，不保证历史完整。
- 用 `git show <commit> -- <path>` 查看具体变化，必要时用 `git show <commit>:<path>` 对照当时的完整文件。要检查旧行为，查看父版本或对应旧实现，不能只看新增行。
- 已知关键符号时，`git log -S '<literal>' -- <path>` 或 `git log -G '<regex>' -- <path>` 可定位相关变化；检查实际 diff 后再确定转折。`blame` 显示最近触及某行的提交，不证明设计起源。
- PR、issue、设计记录和测试可补充变更理由、行为预期与失败情境。测试文件显示其检查的约束；未运行时不声称测试已通过，离线检查也不能证明真实外部服务行为。

## 按语义组织，而非按 diff 规模排序

优先考虑：改变用户行为、接口或数据模型、状态归属、故障恢复、信任边界、核心抽象与关键取舍的变化。搬目录、格式化、生成代码通常只作背景；确实改变使用方式时再纳入。

将分散的小提交合并成一个有证据的设计转折，把批量迁移拆出不同动机。需要时跟进引入后的修复、回滚和分叉，避免把“曾合入”误当作“仍在使用”。发布标题、提交消息只是线索，不能独立证明行为或收益。

一次合并可能被压缩为一个提交，浅克隆、导入仓库、文件搬迁和缺失讨论也会遮住历史。标出缺口及影响；补查可访问的一手记录。无法补齐时，缩小主张，不补写作者动机。

## 将行为、理由与推断分开

对关键转折至少保留可定位的版本/提交与路径；依赖讨论时标出对应链接或本地材料位置。引用只需足够复查，不堆完整日志。

例如代码新增 `task_id`，可证明请求增加了标识；是否用于防重复需要相应依据；是否真正避免重复外部效果还要看接收方协议与实际处理。一个符号、注释或事后偏好不能独立证明完整架构和作者意图。

最后沿当前执行路径重走一次，确认讲到的机制仍然存在、责任如何衔接、在哪个失败窗口仍不成立。区分历史版本事实、当前读取到的行为、实际执行验证与未验证部分。
